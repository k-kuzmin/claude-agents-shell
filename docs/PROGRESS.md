### Протокол моста — фактическая форма

Из C# на страницу (5 типов, как в разделе 3.2 ТЗ; у `out` добавлено поле `seq`):

    { "type": "out",    "id": "t1", "seq": 12, "b64": "<сырые байты PTY в base64>" }
    { "type": "create", "id": "t1", "title": "Домовой · sensor repo" }
    { "type": "show",   "id": "t1" }
    { "type": "close",  "id": "t1" }
    { "type": "exited", "id": "t1", "code": 0 }

Со страницы в C# (3 типа из ТЗ + служебный `ack`):

    { "type": "in",     "id": "t1", "b64": "<байты ввода>" }
    { "type": "resize", "id": "t1", "cols": 120, "rows": 34 }
    { "type": "ready",  "id": "t1" }
    { "type": "ack",    "id": "t1", "seq": 12 }

`seq` в `ack` обязателен: отрицательный, нечисловой или отсутствующий → сообщение отвергается.
Подтверждение накрывает пачку и все более ранние.

### Решения в контрактах

- `IPtySession.ReadAsync(Memory<byte>, ct)` — **pull-модель**. Темпом чтения владеет вызывающий,
  поэтому backpressure из раздела 3.3 ТЗ реализуется без дополнительного канала.
- `ITerminalBridge` живёт в `Application`, реализация с WebView2 — в `App`. Проект `Terminal`
  не имеет ссылки на WebView2.
- **Инвариант `WriteOutputAsync`:** задача завершается **по подтверждению страницы**, а не по факту
  отправки, и `payload` вычитывается **до первого `await`** (буфер возвращается в пул раньше, чем
  завершится задача). Реализация без этих двух свойств молча выключает backpressure и портит память.
- `ShellNotFoundException` вместо `InvalidOperationException` — обработчик, ловящий базовый тип,
  заодно проглатывает дефекты потоков WPF и показывает их как «нет оболочки».

## Корневая причина «вывод мимо псевдоконсоли» — найдена

Симптом: в конфигурации, где у родительского процесса есть стандартные хэндлы (запуск из
терминала, `Start-Process -NoNewWindow`, хост xunit), в пайп приходили только 16 байт преамбулы
ConPTY, а вывод оболочки уходил в консоль родителя. Исполнитель причину не нашёл и записал
наблюдения без объяснения; ревьювер нашёл и проверил матрицей на автономном стенде.

Причина: в `STARTUPINFO` не выставлен `STARTF_USESTDHANDLES`, `dwFlags` оставался 0. Без флага
`CreateProcess` протаскивает в `RTL_USER_PROCESS_PARAMETERS` дочернего процесса стандартные хэндлы
**родителя**, и оболочка пишет туда. 16 байт в пайпе — это конхост, подключённый правильно.

| bInheritHandles | STARTF_USESTDHANDLES | прочитано | маркер |
|---|---|---|---|
| false | нет | 16 байт | MISSING |
| true | нет | 16 байт | MISSING |
| false | да, `hStd*` = NULL | 118 байт | **FOUND** |
| true | да, `hStd*` = NULL | 118 байт | **FOUND** |

`bInheritHandles` ни при чём (EchoCon тоже передаёт FALSE), флаги создания процесса и время жизни
списка атрибутов были корректны. Правка: `dwFlags = STARTF_USESTDHANDLES`, `hStd*` — нули; так же
сделано в `ConptyConnection` Windows Terminal. Проверено на настоящей фабрике из репозитория:
16 → 116 байт, маркер найден. Тесты перестали зависеть от окружения запуска (одинаковый результат из Git Bash и из PowerShell).

Это был не артефакт xunit: запуск приложения из терминала или `dotnet run` давал пустой терминал,
то есть приёмка M1 прошла бы только случайно — из проводника.

### Побочная находка исполнителя — дефект в продакшене

`TerminalPump.DisposeAsync` отписывался от `_pty.Exited` **первой же строкой**, до закрытия
псевдоконсоли. Закрытие гасило оболочку, `Exited` поднимался, слушать было некому, `_exitSignal`
не взводился, и `NotifyExitedAsync` дожидался таймаута: **каждое закрытие вкладки задерживало
отправку кода выхода на страницу ровно на 2 с**, а на выходе из приложения этот простой съедал
бюджет читающего цикла. Отписка перенесена в конец. Прогон тестов 10 с → ~0,7 с.

Побочно это закрыло находку раунда 2 про потерю буферов: ветка `!loopFinished` была достижима
штатно, потому что 2 из 3 с бюджета цикла выжигались впустую. Теперь цикл выходит за десятки
миллисекунд, и остаётся только сценарий реально зависшего чтения из PTY.

### Отступление, одобренное ревьювером

По самостоятельному выходу оболочки зовётся `CloseAsync(terminalId, notifyPage: false)`, а не
полный `CloseAsync`, как было написано в задании оркестратора. Полный шлёт странице `close`,
та делает `term.dispose()` и удаляет узел — то есть пользователь, набравший `exit`, увидел бы
«процесс завершился с кодом 0» и тут же потерял вкладку вместе со всей историей. Раздел 8 ТЗ
требует обратного: вкладка остаётся открытой с пометкой о коде выхода. Ревьювер подтвердил, что
буква задания противоречила ТЗ и выбор верен.

**Хвост на M2:** при `notifyPage: false` воркспейс вычищает и `_pumps`, и `_pending`, то есть
о существовании этой страничной вкладки больше не знает никто — закрыть её потом нечем. В M1
безвредно (одна вкладка, гашение при выходе), в M2 панель вкладок потребует отдельного состояния
«вышла, но жива».

### Как закрыты

- **Защёлка.** Слиты были два разных события, теперь разведены: снятие учёта вкладки
  (`TryRemove` при закрытии) и остановка квитирования на уровне моста (`StopAcknowledgements`,
  включается там, где страницы больше нет — `OnProcessFailed` и `DisposeAsync`). Учёт выдаётся
  через `GetOrCreateRegistry`, который при остановленном квитировании отдаёт реестр уже
  защёлкнутым, плюс повторная проверка после `PostAsync` — на случай остановки во время отправки.
  Одной защёлки в реестре было недостаточно по причине из находки: экземпляр уходит из словаря
  вместе с `TryRemove`. `IsReleased` теперь используется, `_released` покрыт четырьмя тестами.
- **Дубликат.** `CloseTerminalAsync` убран, освобождается только лишняя помпа. Причина записана
  в XML-комментарии, чтобы следующий не «починил» обратно.
- **`NotifyExitedAsync`** стал идемпотентным (`Interlocked`) и вызывается гарантированно: если цикл
  не уложился в 3 с, помпа шлёт `exited` сама, что заодно снимает учёт вкладки, отпускает
  застрявший финальный `FlushAsync(CancellationToken.None)` вместе с буфером и даёт циклу ещё 2 с
  на нормальный выход. Ветка не просто отмечена — она стала выходить штатно.
- **Двойной клик по крестику.** `e.Cancel = true` ставится на **каждой** попытке, пока гашение
  не завершено; `_shutdownCompleted` взводится в `finally` перед `Close()`. Проверено стендом,
  который сначала воспроизводит дефект на старой логике («гашение завершено = False»), потом
  показывает, что правка его снимает.
- **Гонка «оболочка вышла в момент закрытия окна»:** гашения, начатые выходом оболочки,
  регистрируются в `_closing` и дожидаются в `DisposeAsync`. Раньше `DisposeAsync` проходил мимо,
  потому что `TryRemove` уже опустошил `_pumps`. Зубастость теста проверена.
- **Фоновые запуски:** `Observe(Task, string)` пишет причину сбоя в `Trace`. Логгер не заводили —
  полноценный журнал приходит вместе с приёмником хуков в M4.

**Переформулировано честно вместо закрытия:** `ReportToTerminal` создаёт учёт для вкладки,
у которой помпы нет вовсе (неудачный запуск оболочки), и снять его можно только при освобождении
моста. Ограничено временем жизни приложения и числом неудачных запусков, со временем не растёт;
строить ради этого реестр «известных вкладок» сочли непропорциональным.

**Пять сессий — держит по обеим осям.** 43,7 МБ через пять вкладок: 40,7 сообщения моста

а `_flushTimer.Dispose()` вызывается вне обеих блокировок.

## Дефекты первой визуальной приёмки

Пользователь назвал три: не работает `Ctrl+V`, не работает `Shift+Enter`, нижний край окна уходит
под панель задач. Первый раунд правок ревью завернуло с двумя блокирующими — обе поучительные.

### `Ctrl+V` — причина была не там, где её искали дважды

**Диагноз оркестратора был неверен.** Я утверждал, что вставку сломала правка
`AreBrowserAcceleratorKeysEnabled = false`, сделанная по находке первого раунда ревью.
Документация Microsoft прямо говорит обратное: настройка «does not disable accelerator keys related
to movement and text editing, such as: … Ctrl+X, Ctrl+C, Ctrl+V».

**Настоящая причина — в самом xterm.js**, найдена ревьювером по вендоренному бандлу.
`evaluateKeyboardEvent` в ветке `default:` отображает `Ctrl+V` (keyCode 86 без Shift/Alt/Meta)
в `0x16`, после чего `_keyDown` вызывает `cancel(e, true)` и тем самым `preventDefault()`.
Отменённый keydown означает, что Chromium не выполняет команду Paste, поэтому обработчик вставки
на скрытой textarea не вызывается **никогда**. Настройка акселераторов на это не влияет вовсе.

Вставку теперь выполняет сама страница: ветка в `attachCustomKeyEventHandler` зовёт
`event.preventDefault()` и идёт через `navigator.clipboard.readText()` в `term.paste()`.
Одного `return false` было бы мало — обработчик вызывается из обычного колбэка `addEventListener`,
и его возврат на действие браузера не влияет.

### `event.key` вместо `event.code` — обходной путь не работал ровно у того, для кого делался

Ветки `Ctrl+Shift+V` и `Ctrl+C` сравнивались по `event.key`, который отражает раскладку: на ЙЦУКЕН
физическая V даёт «м», C — «с», R — «к». У пользователя русская раскладка, то есть обходной путь,
добавленный ради неработающей вставки, на ней же и не работал бы. Проверив две нерабочие
комбинации подряд, пользователь сделал бы неверный вывод о причине.

## Принятые замечания

- **`0x16` (quoted-insert в readline) через `Ctrl+V` больше не ввести** — цена решения пользователя
  «`Ctrl+V` вставляет». В Claude Code quoted-insert не нужен.
- **`Ctrl+C` с выделением копирует, без выделения шлёт `SIGINT`** — как в Windows Terminal, решение
  пользователя. Ревьювер возражал: случайное выделение мышью молча превращает попытку прервать
  агента в копирование. Принято с этой оговоркой.
- **Правки клавиатурного слоя автотестами не покрыты** — `App` тянет WPF и `Dispatcher`, GUI
  в контейнере не запускается. Проверяются только руками, порядок проверки ниже.

- **Строка `out` попадает в LOH при пачке от ~31,8 КБ.** Порог LOH поднят до 196 608, но точка
  перехода лежит ниже 64 КБ: 31 744 Б → gen 0, 32 768 Б и больше → gen 2. При пяти вкладках
  порога 64 КБ не достигает ни одна пачка (сброс ведёт кадр 16 мс), но ~15 % пачек перешагивают
  31,8 КБ. Принято: измеренная доля пауз GC 0,14–0,20 %, куча 6–30 МБ. Единственная ручка для
  нуля LOH на этом пути — `FlushThresholdBytes` ниже 31 КБ **и** ёмкость аккумулятора ≤ 64 КБ,
  чтобы `ArrayPool` не выдавал 128-килобайтные массивы, ценой примерно двукратного роста числа
  сообщений. Сейчас менять нечего.
- **Фактический предел незавершённых записей — `MaxPendingWrites + 1`, а не `MaxPendingWrites`.**
  Читающий цикл блокируется при `_pending.Count >= 4` и больше четырёх поставить не может,
  а `FlushFromTimerAsync → FlushAsync` ставит пачку, не сверяясь со счётчиком. При пяти вкладках
  не проявляется (наблюдалось 2–3), на 20 вкладках даёт 5. Цена — один лишний кадр и одна пачка
  ~20 КБ в полёте на вкладку.
- **Самовышедшая вкладка остаётся на странице со всем своим следом** — узел, экземпляр `Terminal`
  со scrollback 5000, подключённый `ResizeObserver`, контекст WebGL. Это требование раздела 8 ТЗ
  (вкладка остаётся с пометкой о коде выхода), и след постоянный, а не растущий: записи прекращены,
  таймеров вхолостую нет. **Задел на M2:** пути закрыть такую вкладку у пользователя пока нет,
  а мёртвая вкладка держит контекст WebGL — при 20 вкладках это упрётся в лимит контекстов
  Chromium на страницу.
- **Задержка ввода при 20 одновременно шумящих вкладках не разобрана** (p50 20,4 / p95 120,6 /
  max 340,2 мс, пул 30 потоков). Подпись нерегулярного планирования, а не равномерного замедления.
  Причин две и они не разделены: анонимные пайпы ConPTY вынуждают `FileStream(isAsync: false)`,
  то есть каждое из 1,42 млн чтений — блокирующая работа в пуле; но и измерительная непрерывность
  самого стенда планируется тем же пулом. За бюджетом M1 (пять сессий) — перемерить в M2
  с разделением времени записи и времени прихода эха.
- **Аллокации `PendingWriteRegistry.CompleteUpTo`** (`_items.Keys.ToArray()` + `List<>` на каждую
  квитанцию, на потоке диспетчера). Ревью считает находкой, аудит — нет, и решает измерение:
  240 байт и 210 нс на пачку при глубине ≤ 4, то есть 3,75 КиБ и 3,4 мкс на МиБ вывода — 0,00014 %
  бюджета. Принято: чинить бесплатно не выходит. **Оговорка:** формулировка «аллокации горячего
  пути — ровно одна строка на пачку» после этого неточна, верная цифра — 2,67 МиБ/МиБ плюс
  указанные 3,75 КиБ.
- **`ManualResetEvent` в `ConPtySession` по таймауту не освобождается.** Закрыть хэндл, который
  остался зарегистрированным в `Unregister`, — это `SetEvent` в переиспользованный чужой объект
  синхронизации. Цена промаха — один хэндл события до финализатора, и `SafeWaitHandle`
  финализируется, так что настоящей утечки нет.
- **`_flushLock` и `_writeLock` не освобождаются вовсе.** `SemaphoreSlim` создаёт `WaitHandle`
  лениво, только под `AvailableWaitHandle`, который в коде не трогается нигде. Решение
  задокументировано в обоих местах.
- **`CancellationToken` не отменяет уже начатое чтение из PTY.** Следствие синхронных анонимных
  пайпов: токен наблюдается только до старта чтения. Поэтому корректность освобождения
  `ConPtySession` и `TerminalPump` держится на таймаутах 2/3/5 с, а не на отмене. Принято: уход на
  именованные пайпы с `FILE_FLAG_OVERLAPPED` — переделка самого рискованного места проекта ради
  того, что измерением не подтверждается как проблема.
- **`DispatcherPriority.Background` ниже не только `Render`, но и `Input`.** При загруженном
  UI-потоке вывод может подождать ввод. Для одного дочернего HWND WebView2 UI-поток почти
  простаивает, риск голодания приемлем.
- **`WebView2TerminalBridge` не покрыт тестами** — `App` тянет WPF и `Dispatcher`. Вся бухгалтерия
  переехала в покрытый `PendingWriteRegistry` (7 тестов), в мосте осталось три оператора.
  Круговой путь `out(seq)` → `app.js` → `ack(seq)` → завершение записи не покрыт ничем: его обрыв
  тихо останавливает вывод. Поэтому в приёмку добавлен конкретный критерий — длительный плотный
  вывод должен доходить до конца; зависание после первых ~4 пачек и есть симптом обрыва квитанций.
- **`WebView2TerminalBridge` принимает целый `TerminalOptions`,** а нужны 2 поля из 7 (ISP).
  Разрезать на один record настроек сейчас дороже пользы; в M2, когда настроек станет больше,
  разрез напросится.

## Решения

- **Сравнение клавиш только по `event.code`** для букв и цифр. `event.key` допустим лишь для
  `Enter`, `F5` и стрелок. Правило нарушается незаметно и проявляется только на неанглийской
  раскладке — держать на виду.
- **`AreBrowserAcceleratorKeysEnabled = false` — осознанно и обязательно.** Выключение глушит
  reserved-класс акселераторов Chromium (`Ctrl+W`, `Ctrl+N`, `Ctrl+T`), который иначе до страницы
  не доходит вовсе и не поддаётся `preventDefault`. Для оболочки `Ctrl+W` — это kill-word.
  `Ctrl+T` понадобится в M2 по разделу 6.3 ТЗ, поэтому менять настройку без проверки этого класса
  нельзя. Новый клавиатурный код от акселераторов не зависит: он ходит в буфер обмена через
  `navigator.clipboard`.
- **Защита от перезагрузки страницы — два рубежа.** Отмена любой навигации после первой в C#
  (жёсткая, не зависит от клавиши и фокуса; флаг взводится в начале первой навигации, а не по её
  завершении) и точечный `preventDefault` на странице **без `stopPropagation`**, чтобы
  `Ctrl+R/F/P/G` доходили до readline. Это заменило снятую настройку акселераторов.
- **`Shift+Enter` в `ESC CR` из коробки** — то, ради чего в других терминалах нужен
  `/terminal-setup`. Не регрессия: `Shift+Enter` не работает и в обычном терминале.
- **Окно вписывается в рабочую область своего монитора** (`MonitorFromWindow` плюс
  `GetMonitorInfo` на `OnSourceInitialized`), с пересчётом в единицы WPF матрицей окна, то есть
  per-monitor DPI учтён; откат на `SystemParameters.WorkArea`.
- **`AcceleratorKeyPressed` не используется:** WPF-контрол не отдаёт `CoreWebView2Controller`
  наружу, подписаться можно только рефлексией по приватному члену — при централизованно
  зафиксированной версии пакета это сломалось бы молча при обновлении.

- **ConPTY напрямую через P/Invoke, без `Pty.Net`.** В NuGet `Pty.Net` доступен только как
  `0.1.16-pre`, стабильной версии нет. Раздел 2 ТЗ прямо допускает собственную обвязку над
  `CreatePseudoConsole`. Плюсом — полный контроль над сырым чтением и ресайзом.
- **xterm.js 5.5.0 + addon-fit 0.10.0 + addon-webgl 0.18.0 + addon-unicode11 0.8.0.** ТЗ требует
  5.x; это последние стабильные аддоны с `peerDependencies` на `@xterm/xterm ^5.0.0`. Аддоны
  0.11 / 0.19 / 0.9 выпущены под xterm 6.
- **Порог LOH поднят, константа 64 КБ из ТЗ сохранена.** `System.GC.LOHThreshold = 196608`
  в `ClaudeAgentsShell.App.csproj` — Gen2 падает с 71 до 1. Альтернатива «`FlushThresholdBytes`
  ≤ 24 КБ» даёт тот же результат ценой 16 → 43 сообщений на МБ, но раздел 3.3 ТЗ фиксирует 64 КБ
  прямо, и менять константу — отступление от ТЗ, требующее согласования. Значение
  в `RuntimeHostConfigurationOption` **десятичное** (переменная `DOTNET_GCLOHThreshold` — hex).
- **Пайпы анонимные (`CreatePipe`), чтение блокирующее на потоке пула.** Точное следование примеру
  Microsoft. Измерено: 5 и 20 припаркованных чтений не дают задержки постановки задач в пул
  (медиана 0,00 мс, максимум 0,41 мс) даже при задавленном минимуме пула.
- **Отступления от протокола раздела 3.2 ТЗ — два, оба вынужденные.** Раздел 3.3 требует счётчик
  незавершённых `term.write`, но канала подтверждения не описывает вовсе:
  1. служебный входящий тип `ack` (девятый тип);
  2. поле `seq` в исходящем `out` — иначе странице неоткуда взять корреляционный номер.
  Альтернатива «страница ведёт встречный счётчик» отвергнута: счётчик обнуляется при пересоздании
  терминала и перезагрузке страницы, а C# перекоса не видит — та же болезнь в менее заметной форме.
  Ревьювер подтвердил, что без расширения `out` требование раздела 3.3 невыполнимо.
  **Ожидает подтверждения пользователя.** Откат на встречный счётчик дешёвый.
- **Учёт квитанций вынесен из `App` в `Terminal.Protocol`** (`PendingWriteRegistry`). Мотив —
  покрываемость тестами: тестовый проект не ссылается на `App`. Раздел 3 CLAUDE.md относит протокол
  к слою `Terminal`, тип не знает ни про WebView2, ни про WPF; зависимость `App → Terminal`
  разрешённая. Ревьювер нарушения не увидел.
- **Целевая платформа `net8.0-windows10.0.17763.0`** для `Terminal`, `App` и тестов — ConPTY требует
  Windows 10 1809. `Domain`, `Application`, `Sessions` — чистый `net8.0`.
- **Централизованные версии пакетов** (`Directory.Packages.props`), чтобы блоки не разъезжались
  по версиям при параллельной работе.
- **Контракты M5 (раскладка, настройки хуков) не фиксировались** — добавляются в начале своего
  этапа, чтобы не плодить мёртвые типы сейчас.

## Повторная приёмка M1 — порядок, разводящий переменные

Порядок важен: начинать с **русской** раскладки. Английская — это тот случай, который работал бы
и со старым кодом на `event.key`, и если начать с неё, мы не узнаем, починена ли вторая
блокирующая находка.

**Сначала, один раз, любая раскладка:**

0. Окно открылось, есть приглашение `powershell.exe`, нижние строки и строка статуса видны
   целиком, окно не уходит под панель задач.

**Блок A — русская раскладка (главный):**

1. Скопировать где-нибудь **многострочный** текст, в терминале нажать `Ctrl+V`. Ожидание: текст
   вставляется одним блоком, без серии Enter. Мусорный символ вместо вставки — правка не сработала;
   браузерный диалог про буфер обмена — не сработала сверка источника разрешения.
2. `Ctrl+Shift+V` — то же самое.
3. Выделить мышью кусок вывода, `Ctrl+C`, вставить в блокнот. Ожидание: скопировалось, выделение
   снялось.
4. Снять выделение, запустить что-нибудь долгое, `Ctrl+C`. Ожидание: прервалось.

**Блок B — английская раскладка:** повторить пункты 1–4. Расхождение с блоком A означает, что
где-то осталось сравнение по `event.key`.

**Блок C — управляющие символы и перезагрузка:**

5. Набрать `echo слово слово` и, не нажимая Enter, нажать `Ctrl+W`. Ожидание: стёрлось последнее
   слово. Это проверка возврата `AreBrowserAcceleratorKeysEnabled = false`.
6. `F5`, затем `Ctrl+R`: страница не перезагружается, вкладка жива. Сразу следом `Ctrl+R`
   в оболочке должен открыть обратный поиск по истории — то есть клавиша дошла до readline.
7. Запустить `claude`, в промпте `Shift+Enter`: перенос строки, а не отправка. Обычный `Enter`
   отправляет.

Пункты 5–6 намеренно последние: даже если они поведут себя неверно, это не помешает выяснить
главное про вставку.

## Прежний список приёмки M1 (пройден)

1. **Дважды кликнуть по крестику подряд** — окно остаётся на экране до конца гашения и закрывается
   один раз; в диспетчере не осталось `powershell.exe`, `conhost.exe`, `OpenConsole.exe`.
2. **Набрать `exit`, затем сразу закрыть окно** — та самая гонка, из-за которой псевдоконсоль
   могла пережить приложение.
3. **Набрать `exit` и остаться** — появляется строка с кодом выхода, **вкладка с историей остаётся
   на экране** (раздел 8 ТЗ), а хост консоли уходит из диспетчера сразу, не дожидаясь закрытия
   приложения, и без прежней двухсекундной задержки.
4. Запуск **из проводника и из терминала** (`dotnet run`, `.\ClaudeAgentsShell.exe`) — в обоих
   случаях приглашение `powershell.exe` (pwsh в PATH нет, работает откат).
5. **`F5` и `Ctrl+R` внутри терминала** — страница не перезагружается, вкладка продолжает работать.
   Правый клик — браузерного меню нет.
6. `claude` руками: TUI, рамки, кириллица, ширина эмодзи (проверка активации unicode11).
7. Ресайз окна за край — без «лесенки» и мусора.
8. Вставка многострочного текста (bracketed paste).

### Протокол моста — фактическая форма

Из C# на страницу (5 типов, как в разделе 3.2 ТЗ; у `out` добавлено поле `seq`):

    { "type": "out",    "id": "t1", "seq": 12, "b64": "<сырые байты PTY в base64>" }
    { "type": "create", "id": "t1", "title": "Домовой · sensor repo" }
    { "type": "show",   "id": "t1" }
    { "type": "close",  "id": "t1" }
    { "type": "exited", "id": "t1", "code": 0 }

Со страницы в C# (3 типа из ТЗ + служебный `ack`):

    { "type": "in",     "id": "t1", "b64": "<байты ввода>" }
    { "type": "resize", "id": "t1", "cols": 120, "rows": 34 }
    { "type": "ready",  "id": "t1" }
    { "type": "ack",    "id": "t1", "seq": 12 }

`seq` в `ack` обязателен: отрицательный, нечисловой или отсутствующий → сообщение отвергается.
Подтверждение накрывает пачку и все более ранние.

### Решения в контрактах

- `IPtySession.ReadAsync(Memory<byte>, ct)` — **pull-модель**. Темпом чтения владеет вызывающий,
  поэтому backpressure из раздела 3.3 ТЗ реализуется без дополнительного канала.
- `ITerminalBridge` живёт в `Application`, реализация с WebView2 — в `App`. Проект `Terminal`
  не имеет ссылки на WebView2.
- **Инвариант `WriteOutputAsync`:** задача завершается **по подтверждению страницы**, а не по факту
  отправки, и `payload` вычитывается **до первого `await`** (буфер возвращается в пул раньше, чем
  завершится задача). Реализация без этих двух свойств молча выключает backpressure и портит память.
- `ShellNotFoundException` вместо `InvalidOperationException` — обработчик, ловящий базовый тип,
  заодно проглатывает дефекты потоков WPF и показывает их как «нет оболочки».

## Корневая причина «вывод мимо псевдоконсоли» — найдена

Симптом: в конфигурации, где у родительского процесса есть стандартные хэндлы (запуск из
терминала, `Start-Process -NoNewWindow`, хост xunit), в пайп приходили только 16 байт преамбулы
ConPTY, а вывод оболочки уходил в консоль родителя. Исполнитель причину не нашёл и записал
наблюдения без объяснения; ревьювер нашёл и проверил матрицей на автономном стенде.

Причина: в `STARTUPINFO` не выставлен `STARTF_USESTDHANDLES`, `dwFlags` оставался 0. Без флага
`CreateProcess` протаскивает в `RTL_USER_PROCESS_PARAMETERS` дочернего процесса стандартные хэндлы
**родителя**, и оболочка пишет туда. 16 байт в пайпе — это конхост, подключённый правильно.

| bInheritHandles | STARTF_USESTDHANDLES | прочитано | маркер |
|---|---|---|---|
| false | нет | 16 байт | MISSING |
| true | нет | 16 байт | MISSING |
| false | да, `hStd*` = NULL | 118 байт | **FOUND** |
| true | да, `hStd*` = NULL | 118 байт | **FOUND** |

`bInheritHandles` ни при чём (EchoCon тоже передаёт FALSE), флаги создания процесса и время жизни
списка атрибутов были корректны. Правка: `dwFlags = STARTF_USESTDHANDLES`, `hStd*` — нули; так же
сделано в `ConptyConnection` Windows Terminal. Проверено на настоящей фабрике из репозитория:
16 → 116 байт, маркер найден. Тесты перестали зависеть от окружения запуска (72 = 72).

Это был не артефакт xunit: запуск приложения из терминала или `dotnet run` давал пустой терминал,
то есть приёмка M1 прошла бы только случайно — из проводника.

## Раунд 1 гейтов — закрыт

Ревью: 1 блокирующая (`STARTF_USESTDHANDLES`) + 10 прочих. Все 11 подтверждены ревьювером как
закрытые во втором раунде. Аудит: 5 рисков, все закрыты (`TryRemove` — частично, см. раунд 2).

Существенное из закрытого:

- **LOH.** Пачка 64 КБ давала строку 175 КБ — каждое сообщение `out` в LOH, каждая сборка Gen0
  становилась полной: 0,89 полной сборки на МБ вывода, пять вкладок × 16 МБ → Gen2=71.
- **`F5` внутри терминала** перезагружал страницу и убивал вкладку насовсем: `CoreWebView2.Settings`
  не настраивались вообще.
- **`_writeLock.WaitAsync` вне `try`** — ввод в момент закрытия окна ронял процесс через `async void`.
- **Порча буфера `ArrayPool`** — при закрытии буфер возвращался в пул, пока цикл чтения в него писал.
- **Квитанции без корреляции** — одна потерянная квитанция выключала backpressure навсегда.

## Принятые замечания

- **`CancellationToken` не отменяет уже начатое чтение из PTY.** Следствие синхронных анонимных
  пайпов: токен наблюдается только до старта чтения. Поэтому корректность освобождения
  `ConPtySession` и `TerminalPump` держится на таймаутах 2/3/5 с, а не на отмене. Принято: уход на
  именованные пайпы с `FILE_FLAG_OVERLAPPED` — переделка самого рискованного места проекта ради
  того, что измерением не подтверждается как проблема.
- **`DispatcherPriority.Background` ниже не только `Render`, но и `Input`.** При загруженном
  UI-потоке вывод может подождать ввод. Для одного дочернего HWND WebView2 UI-поток почти
  простаивает, риск голодания приемлем.
- **`WebView2TerminalBridge` не покрыт тестами** — `App` тянет WPF и `Dispatcher`. Вся бухгалтерия
  переехала в покрытый `PendingWriteRegistry` (7 тестов), в мосте осталось три оператора.
  Круговой путь `out(seq)` → `app.js` → `ack(seq)` → завершение записи не покрыт ничем: его обрыв
  тихо останавливает вывод. Поэтому в приёмку добавлен конкретный критерий — длительный плотный
  вывод должен доходить до конца; зависание после первых ~4 пачек и есть симптом обрыва квитанций.
- **`WebView2TerminalBridge` принимает целый `TerminalOptions`,** а нужны 2 поля из 7 (ISP).
  Разрезать на один record настроек сейчас дороже пользы; в M2, когда настроек станет больше,
  разрез напросится.

## Решения

- **ConPTY напрямую через P/Invoke, без `Pty.Net`.** В NuGet `Pty.Net` доступен только как
  `0.1.16-pre`, стабильной версии нет. Раздел 2 ТЗ прямо допускает собственную обвязку над
  `CreatePseudoConsole`. Плюсом — полный контроль над сырым чтением и ресайзом.
- **xterm.js 5.5.0 + addon-fit 0.10.0 + addon-webgl 0.18.0 + addon-unicode11 0.8.0.** ТЗ требует
  5.x; это последние стабильные аддоны с `peerDependencies` на `@xterm/xterm ^5.0.0`. Аддоны
  0.11 / 0.19 / 0.9 выпущены под xterm 6.
- **Порог LOH поднят, константа 64 КБ из ТЗ сохранена.** `System.GC.LOHThreshold = 196608`
  в `ClaudeAgentsShell.App.csproj` — Gen2 падает с 71 до 1. Альтернатива «`FlushThresholdBytes`
  ≤ 24 КБ» даёт тот же результат ценой 16 → 43 сообщений на МБ, но раздел 3.3 ТЗ фиксирует 64 КБ
  прямо, и менять константу — отступление от ТЗ, требующее согласования. Значение
  в `RuntimeHostConfigurationOption` **десятичное** (переменная `DOTNET_GCLOHThreshold` — hex).
- **Пайпы анонимные (`CreatePipe`), чтение блокирующее на потоке пула.** Точное следование примеру
  Microsoft. Измерено: 5 и 20 припаркованных чтений не дают задержки постановки задач в пул
  (медиана 0,00 мс, максимум 0,41 мс) даже при задавленном минимуме пула.
- **Отступления от протокола раздела 3.2 ТЗ — два, оба вынужденные.** Раздел 3.3 требует счётчик
  незавершённых `term.write`, но канала подтверждения не описывает вовсе:
  1. служебный входящий тип `ack` (девятый тип);
  2. поле `seq` в исходящем `out` — иначе странице неоткуда взять корреляционный номер.
  Альтернатива «страница ведёт встречный счётчик» отвергнута: счётчик обнуляется при пересоздании
  терминала и перезагрузке страницы, а C# перекоса не видит — та же болезнь в менее заметной форме.
  Ревьювер подтвердил, что без расширения `out` требование раздела 3.3 невыполнимо.
  **Ожидает подтверждения пользователя.** Откат на встречный счётчик дешёвый.
- **Учёт квитанций вынесен из `App` в `Terminal.Protocol`** (`PendingWriteRegistry`). Мотив —
  покрываемость тестами: тестовый проект не ссылается на `App`. Раздел 3 CLAUDE.md относит протокол
  к слою `Terminal`, тип не знает ни про WebView2, ни про WPF; зависимость `App → Terminal`
  разрешённая. Ревьювер нарушения не увидел.
- **Целевая платформа `net8.0-windows10.0.17763.0`** для `Terminal`, `App` и тестов — ConPTY требует
  Windows 10 1809. `Domain`, `Application`, `Sessions` — чистый `net8.0`.
- **Централизованные версии пакетов** (`Directory.Packages.props`), чтобы блоки не разъезжались
  по версиям при параллельной работе.
- **Контракты M5 (раскладка, настройки хуков) не фиксировались** — добавляются в начале своего
  этапа, чтобы не плодить мёртвые типы сейчас.

## Приёмка M1 — что проверяет пользователь

1. Запуск **из проводника и из терминала** (`dotnet run`, `.\ClaudeAgentsShell.exe`) — в обоих
   случаях приглашение `powershell.exe` (pwsh в PATH нет, работает откат).
2. **`F5` и `Ctrl+R` внутри терминала** — страница не перезагружается, вкладка продолжает работать.
   Правый клик — браузерного меню нет.
3. `claude` руками: TUI, рамки, кириллица, ширина эмодзи (проверка активации unicode11).
4. Ресайз окна за край — без «лесенки» и мусора.
5. Вставка многострочного текста (bracketed paste).
6. `dotnet build` на среднем решении: UI отзывчив, ввод без задержки. **Отдельно: длительный плотный
   вывод должен дойти до конца.** Остановка после первых ~4 пачек — симптом обрыва квитанций.
7. Набор текста **в момент закрытия окна** — процесс не падает.
8. После закрытия окна в диспетчере задач не осталось `powershell.exe`, `conhost.exe` и приложения.

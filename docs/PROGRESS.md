## Зафиксированные контракты

Коммит `a7aea33`. Меняются только оркестратором.

**Domain** (без зависимостей): `TerminalId`, `TerminalSize`, `ShellKind`, `ShellStartCommand`,
`PtyStartInfo`, `SessionLaunch` (`NewSession` / `ResumeSession` / `ContinueLast`), `TabState`,
`ProjectDefinition`, `SessionSummary`, `HookEvent` + `HookKind`.

**Application.Ports**: `IPtySession` (+`IPtySessionFactory`, `PtyStartException`),
`IShellProvider` / `IShellResolver`, `ITerminalBridge` (+ три EventArgs,
`TerminalBridgeUnavailableException`), `IProjectStore`, `ISessionHistoryReader`, `IHookListener`.

**Terminal.Protocol**: `InboundBridgeMessage` (`Input` / `Resize` / `Ready`),
`IBridgeMessageWriter`, `IBridgeMessageParser`, `TerminalOptions` (кадр 16 мс, порог 64 КБ,
буфер чтения 16 КБ, `MaxPendingWrites` = 4, scrollback 5000, дебаунс ресайза 80 мс).

Ключевые решения в контрактах:

- `IPtySession.ReadAsync(Memory<byte>, ct)` — **pull-модель**. Темпом чтения владеет вызывающий,
  поэтому backpressure из раздела 3.3 ТЗ реализуется без дополнительного канала.
- `ITerminalBridge` живёт в `Application`, реализация с WebView2 — в `App`. Проект `Terminal`
  не имеет ссылки на WebView2.
- Протокол моста — ровно 5 + 3 типа сообщений из раздела 3.2 ТЗ, без расширений.
  Поля `cols`/`rows` в `ready` не добавлены: страница шлёт `ready`, затем `fit()`, затем `resize`.

### Находки аудита производительности M1

Все подтверждены измерением на стенде аудитора (16 ядер, Release).

| № | Где | Суть | Статус |
|---|---|---|---|
| 1 | `TerminalOptions.cs:12`, `BridgeMessageWriter.cs:20-55` | Пачка 64 КБ → строка 175 КБ → **LOH**. 0,89 полной сборки мусора на МБ вывода; 5 вкладок × 16 МБ дают Gen2=71 | чинится вариантом (а), см. Решения |
| 2 | `web/app.js:241-252`, `WebView2TerminalBridge.cs:142-166` | Страница не шлёт `ack`, если вкладки уже нет. Очередь квитанций FIFO без корреляции — одна потеря выключает backpressure навсегда, помпа встаёт | чинится сейчас; в M1 недостижимо, блокирующий с M2 |
| 3 | `WebView2TerminalBridge.cs:252` | `DispatcherPriority.Send` на каждый `out` — выше `Render`. В M2 вытеснит отрисовку оболочки | чинится сейчас |
| 4 | `OutputAccumulator.cs:36-71` | Начальная ёмкость 16 КБ при пороге 64 КБ — рост буфера и лишние 48 КБ memcpy на каждую пачку | чинится сейчас |
| 5 | `WebView2TerminalBridge.cs:312-323` | `ReleaseAcknowledgements` не делает `TryRemove` — запись словаря остаётся на каждую закрытую вкладку | чинится сейчас |

## Принятые замечания

Находки ревью и аудита, которые решено не чинить, с обоснованием.

- **`CancellationToken` не отменяет уже начатое чтение из PTY.** Следствие синхронных анонимных
  пайпов (см. Решения): токен наблюдается только до старта чтения. Поэтому корректность
  освобождения `ConPtySession` и `TerminalPump` держится на таймаутах 2/3/5 с, а не на отмене.
  Принято: уход на именованные пайпы с `FILE_FLAG_OVERLAPPED` — переделка самого рискованного
  места проекта ради того, что измерением не подтверждается как проблема.
- **Константы `SCROLLBACK` и `RESIZE_DEBOUNCE_MS` продублированы** в `web/app.js` и
  `TerminalOptions`. Расхождение не поймает ни компилятор, ни тест. Принято: единственная
  альтернатива — генерировать конфиг страницы из C#, что дороже риска.

## Решения

- **ConPTY напрямую через P/Invoke, без `Pty.Net`.** В NuGet `Pty.Net` доступен только как
  `0.1.16-pre` (предрелиз, без стабильной версии). Раздел 2 ТЗ прямо допускает собственную
  обвязку над `CreatePseudoConsole`. Плюсом получаем полный контроль над сырым чтением и ресайзом.
- **xterm.js 5.5.0 + addon-fit 0.10.0 + addon-webgl 0.18.0 + addon-unicode11 0.8.0.**
  ТЗ требует 5.x; это последние стабильные аддоны, у которых `peerDependencies` указывает
  `@xterm/xterm ^5.0.0`. Более новые аддоны (0.11 / 0.19 / 0.9) выпущены под xterm 6.
- **Целевая платформа `net8.0-windows10.0.17763.0`** для `Terminal`, `App` и тестов —
  ConPTY требует Windows 10 1809. `Domain`, `Application`, `Sessions` — чистый `net8.0`.
- **Централизованные версии пакетов** (`Directory.Packages.props`), чтобы блоки не разъезжались
  по версиям при параллельной работе.
- **Порог LOH поднимается, константа 64 КБ из ТЗ сохраняется.** Аудит показал: пачка 64 КБ
  даёт строку 175 КБ, то есть каждое сообщение `out` попадает в LOH и каждая сборка Gen0
  становится полной. Два измеренных лечения: (а) `System.GC.LOHThreshold = 196608` в csproj
  приложения — Gen2 падает с 71 до 1; (б) `FlushThresholdBytes ≤ 24 КБ` — тот же результат,
  цена 16 → 43 сообщения на МБ. Выбран (а): раздел 3.3 ТЗ фиксирует «64 КБ» прямо, и менять
  константу — отступление от ТЗ, требующее согласования, тогда как (а) даёт тот же эффект
  без него. Значение в `RuntimeHostConfigurationOption` — десятичное (в отличие от переменной
  окружения `DOTNET_GCLOHThreshold`, которая читается как hex).
- **Пайпы анонимные (`CreatePipe`), чтение блокирующее на потоке пула.** Точное следование
  официальному примеру Microsoft. Аудит измерил: 5 и даже 20 припаркованных чтений не дают
  задержки постановки задач в пул (медиана 0,00 мс, максимум 0,41 мс) даже при искусственно
  задавленном минимуме пула. Отход на `FILE_FLAG_OVERLAPPED` в M1 не нужен.
- **Один служебный входящий тип `ack`** (`{"type":"ack","id":"t1","bytes":N}`) сверх восьми
  типов раздела 3.2 ТЗ. Раздел 3.3 прямо требует счётчик незавершённых `term.write`, но канала
  подтверждения не описывает — без девятого типа требование невыполнимо. Пять исходящих типов
  не тронуты.
- **Инвариант «payload вычитывается до первого `await`»** зафиксирован в XML-доке
  `ITerminalBridge.WriteOutputAsync`: буфер возвращается в пул до завершения задачи записи.
  Вторая реализация моста без этого инварианта даёт порчу памяти.
- **Контракты M5 (раскладка, настройки хуков) не фиксировались** — они добавляются в начале
  своего этапа, чтобы не плодить мёртвые типы сейчас.

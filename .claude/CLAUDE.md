# CLAUDE.md — Claude Agents Shell

WPF-оболочка над терминалом для параллельной работы с несколькими сессиями Claude Code.
Полное ТЗ: `docs/TZ.md`. Макет: `docs/mockup.html`. **Оба читаются один раз в начале, целиком; дальше опираемся на них, а не перечитываем.**

Этот файл попадает в контекст каждого агента — он короткий намеренно. Детали живут в ТЗ.

---

## 1. Роль главного окна: оркестратор

Главная сессия **не пишет продакшн-код**. Она:

1. читает ТЗ, строит план по этапам;
2. фиксирует контракты (интерфейсы и модели) — это единственный код, который она пишет сама;
3. дробит этап на блоки и запускает под каждый блок сабагента;
4. принимает результаты, прогоняет ревью и аудит производительности;
5. ведёт `docs/PROGRESS.md`.

Правила:

- Сама редактирует файл, только если правка — меньше ~30 строк и это склейка между блоками. Всё остальное делегируется.
- Никогда не читает файлы реализации целиком, чтобы «посмотреть, что получилось». Для этого есть ревьювер.
- Не держит состояние проекта в контексте. Состояние — в `docs/PROGRESS.md`: что сделано, какие контракты зафиксированы, что провалило ревью. После каждого блока файл обновляется.
- Сабагент возвращает **сводку**: что сделано, какие файлы затронуты, какие решения приняты, что осталось. Не содержимое файлов.
- Если в ТЗ что-то противоречиво или не описано — спросить пользователя, а не додумывать. Одно уточнение лучше, чем ветка кода, которую придётся выбрасывать.

## 2. Параллельность

**Контракты вперёд.** Перед запуском параллельных блоков оркестратор пишет интерфейсы, DTO и сигнатуры сообщений моста. После этого сабагенты работают за интерфейсами и не блокируют друг друга.

**Один блок — одна папка.** Два агента никогда не редактируют один файл. Если блокам нужен общий файл (DI-регистрация, `.csproj`, страница терминалов) — его правит оркестратор после того, как блоки закончили.

**Запуск.** Независимые блоки стартуют одним сообщением с несколькими вызовами агента — тогда они выполняются одновременно. Последовательно запускаются только зависимые.

**Гранулярность.** Блок — это вертикальный срез на несколько часов работы, а не отдельный класс. Ориентир: 3–5 блоков на этап.

**Что не параллелится:**

- Этап M1 (мост ConPTY ↔ WebView2) делается одним агентом последовательно. Это фундамент, и его корректность проверяется глазами человека — эмодзи, рамки TUI, ресайз. Пока M1 не принят пользователем, следующие этапы не начинаются.
- Правки по результатам ревью возвращаются **тому же** агенту, который писал блок, через продолжение его сессии — у него уже есть контекст.

## 3. Архитектура

Зависимости направлены внутрь: `App → Sessions/Terminal → Domain`. Обратных ссылок нет.

```
src/ClaudeAgentsShell.Domain        модели, без зависимостей вообще
src/ClaudeAgentsShell.Application   порты (интерфейсы), сценарии
src/ClaudeAgentsShell.Terminal      ConPTY, мост, протокол сообщений
src/ClaudeAgentsShell.Sessions      projects.json, история, приёмник хуков
src/ClaudeAgentsShell.App           WPF, ViewModel, DI-композиция
web/                                страница терминалов, xterm.js локально
tests/                              модульные тесты
```

Правила, которые проверяет ревьювер:

- **SRP.** Класс делает одно. `PtySession` не знает про вкладки; `TabViewModel` не знает про ConPTY; парсер `.jsonl` не знает про UI.
- **DIP.** Прикладной код зависит от интерфейсов: `IPtySession`, `IPtySessionFactory`, `IProjectStore`, `ISessionHistoryReader`, `IHookListener`, `ITerminalBridge`. Конкретные реализации подставляются в DI.
- **OCP.** Новая оболочка (pwsh/powershell/cmd) или новый источник состояния вкладки добавляются реализацией интерфейса, а не `switch` по типу.
- **ISP.** Никаких интерфейсов-помоек. Если реализации нужна половина методов — интерфейс надо разрезать.
- В ViewModel нет `File.*`, `Process.*`, P/Invoke и прямых вызовов WebView2. Только порты.
- DI — `Microsoft.Extensions.DependencyInjection`, композиция в одном месте. Статических синглтонов и service locator нет.
- `async void` только в обработчиках событий. Везде остальное — `Task` с `CancellationToken`.
- Всё, что владеет ресурсом, реализует `IDisposable`/`IAsyncDisposable` и освобождается детерминированно.

Nullable reference types включены, предупреждения компилятора = ошибки.

## 4. Специализированные агенты

Определения в `.claude/agents/`.

| Агент | Когда |
|---|---|
| `reviewer` | после каждого блока и обязательно в конце этапа |
| `perf-auditor` | в конце каждого этапа; для M1 и M2 — обязательно |

**Ревьювер** получает диапазон изменений и проверяет соответствие ТЗ и разделу 3. Он не правит код — возвращает список находок с указанием файла и строки, отсортированный по серьёзности. Оркестратор раздаёт находки исполнителям.

**Аудитор производительности** проверяет горячие пути этого проекта, а не абстрактную оптимизацию. Его чеклист — в его определении.

Этап считается закрытым, когда ревьювер и аудитор возвращают пустой список либо только осознанно принятые замечания, записанные в `docs/PROGRESS.md`.

## 5. Определение готовности блока

1. `dotnet build` без предупреждений.
2. `dotnet test` зелёный; новая логика покрыта тестами.
3. Публичные типы и порты имеют XML-комментарии там, где назначение не очевидно из имени.
4. Никаких TODO без привязки к пункту ТЗ.
5. Изменения закоммичены одним осмысленным коммитом с описанием блока.

Ветка на этап: `stage/m1-pty-bridge`, `stage/m2-tabs` и так далее.

## 6. Команды

```
dotnet build ClaudeAgentsShell.sln
dotnet test tests/…
dotnet format --verify-no-changes
```

Приложение запускается только на Windows с установленным WebView2 Runtime. Агент в контейнере собирает и тестирует, но **не запускает** GUI — визуальную проверку делает пользователь.

## 7. Запреты, специфичные для проекта

Нарушение любого пункта — блокирующая находка на ревью.

- **Один WebView2 на окно.** Контрол на вкладку недопустим.
- **Вывод PTY передаётся как base64 сырых байтов.** Декодировать чанки в `string` на стороне C# нельзя: чанк рвётся посреди UTF-8 последовательности и ломает кириллицу и рамки TUI.
- **Байты из PTY склеиваются в пачки** (кадр ~16 мс или 64 КБ) перед отправкой на страницу. Отправка каждого чанка по отдельности запрещена.
- **Никаких CDN.** xterm.js и аддоны лежат локально, отдаются через `SetVirtualHostNameToFolderMapping`.
- **Файлы сессий Claude Code только читаются.** Ни удаления, ни записи в `~/.claude/projects`.
- **В проект пользователя ничего не пишется.** Настройки для хуков генерируются в каталоге приложения и передаются сессии через `--settings`.
- **Никакого периодического опроса** каталогов и процессов. Только `FileSystemWatcher` и события хуков.
- **Вывод агента не парсится** для определения состояния вкладки. Источник состояния — хуки.
- Формат `.jsonl` считается нестабильным: любой сбой разбора деградирует до «имя файла и дата», но не роняет приложение.

---

## 8. Гигиена контекста

- Поиск по коду — точечный, по символу или шаблону. `cat` на большой файл не делается ни оркестратором, ни сабагентом.
- Сабагент читает только свою папку и файл контрактов.
- Длинные результаты сборки и тестов не пересказываются целиком: только вердикт и упавшие тесты.
- Если оркестратору нужно вспомнить, что происходит — он читает `docs/PROGRESS.md`, а не историю диалога.
